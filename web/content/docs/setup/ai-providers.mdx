BlazeResolver uses a model in two places: **triage** in your report endpoint, and the **fix engine** in the workflow. Both read keys the same way, and you never have to say which provider a key belongs to.

```bash title=".env"
API_KEYS=sk-ant-...,gsk_...,nvapi-...     # Anthropic, Groq and NVIDIA NIM, in one line
```

Put the same value in the repo secret the workflow reads:

```bash
gh secret set API_KEYS
```

Without any key, triage falls back to keyword rules and the fix engine stops with a clear error on the issue. Check what was recognized, in failover order, with keys masked:

```bash
npx blazeresolver providers
```

## How a key is recognized

Cheapest first:

1. **Its variable name.** `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY` and so on, plus common aliases such as `GOOGLE_API_KEY` and `HF_TOKEN`.
2. **Its format.** Most providers use a distinctive prefix: `sk-ant-`, `gsk_`, `nvapi-`, `AIza`, `xai-`, `pplx-`, `hf_` and others.
3. **Asking, if you opt in.** Keys whose format says nothing (Mistral, Together, Cohere and others) are skipped with a warning by default. With `BLAZE_KEY_PROBE=on`, the likely providers are each asked once whether the key is theirs. It's a model-list request, so no tokens are spent, and the answer is cached. This is off by default because it shows the key to providers it may not belong to.

**Ways to write keys.** Any of these forms work:

| Form | Example |
| :--- | :--- |
| Universal list | `API_KEYS=key1,key2` |
| Universal single or numbered | `API_KEY=...`, `API_KEY_1=...`, `API_KEY_2=...` |
| Named | `MISTRAL_API_KEY=...` |
| Named list or numbered | `GROQ_API_KEYS=a,b` or `GROQ_API_KEY_1=...`, `GROQ_API_KEY_2=...` |

## Failover and rotation

- **Several providers:** the first one in the priority order below answers. When it fails (outage, rate limit, bad key, timeout, unknown model), the next one takes over automatically. A provider that just failed sits out for a minute.
- **Several keys for one provider:** they rotate round-robin. A key that hits an auth or rate-limit error cools down while the others carry on.
- **`BLAZE_PROVIDER=groq`** pins a single provider, and all keys go to it.
- **`BLAZE_MODEL=claude-sonnet-5`** overrides the model, but only on providers that serve it. A Claude model name never reaches Groq. The provider that owns the model moves to the front.
- **`<NAME>_MODEL`** (for example `GROQ_MODEL`) overrides the model for one provider only.

<Callout title="GitHub tokens are never used as AI keys by accident">
  Only a GitHub token pasted into an AI key variable counts as a GitHub Models key. `BLAZE_GITHUB_TOKEN` and `GITHUB_TOKEN` are never used for AI; they stay scoped to issues and pull requests.
</Callout>

**Custom endpoints.** `OPENAI_BASE_URL` points the OpenAI provider at any OpenAI-compatible server. `NVIDIA_BASE_URL` and `OLLAMA_BASE_URL` do the same for their providers. `AZURE_OPENAI_API_VERSION` defaults to `2024-08-01-preview`.

## Keys the workflow can see

The generated workflow passes these to the fix job:

```yaml
API_KEYS: ${{ secrets.API_KEYS }}
ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
BLAZE_PROVIDER: ${{ vars.BLAZE_PROVIDER }}
BLAZE_MODEL: ${{ vars.BLAZE_MODEL }}
```

Any key that `API_KEYS` can recognize just works. If you use a **named variable** (for example `MISTRAL_API_KEY`, or Azure's endpoint settings), add it as a repo secret **and** add a matching line under `env:` in `.github/workflows/blazeresolver.yml`.

<Callout type="info" title="Which model for fixes?">
  Triage is short and cheap, so any model works. The fix engine reads code and writes precise edits, so it does noticeably better on a strong coding model. A good setup is a strong model first for quality, then a free-tier key as the failover.
</Callout>
