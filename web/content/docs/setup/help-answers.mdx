---
title: Answer questions from your docs
description: Customers who ask how to do something get an answer from your README and help docs, right in the widget.
---

Not every message is a bug. When [triage](/docs/concepts/triage) decides a report is a **how-to question** ("how do I export my data?"), the endpoint tries to answer it from your documentation before it replies. The answer appears in the widget under **Here's what we found**. Nothing is filed on GitHub.

It works out of the box: the repo's README is the source. You can add more docs.

## How it works

1. **Only questions.** Answering runs only for messages triage classifies as questions, only when an AI key is configured, and never for a report the injection screen flagged.
2. **Collect the docs.** The endpoint reads your product's README straight from disk: the one at the root of the app's checkout (or its working directory, when deployed without `.git`), as long as that checkout's GitHub remote is the `repo` you passed. No token or network call is needed, private repos work, and edits are picked up as soon as the file changes. Where no README is deployed with the app, it fetches the README of `repo` from GitHub instead, with your token first, then without it. A public repo needs no token; a private one needs `BLAZE_GITHUB_TOKEN` to have **Contents: read-only**. When the README can't be read, the endpoint logs a warning once and answers from `helpDocs` alone. READMEs are cached for 10 minutes; a failed fetch is retried after a minute. Any extra `helpDocs` you pass are added.
3. **Find the relevant sections.** The docs are split at their headings into sections of about 1,200 characters, and ranked against the question two ways: by keywords (BM25), and by meaning when an [embeddings provider](#semantic-search) is configured. The two rankings are merged (reciprocal rank fusion) and the top 4 sections go to the model.
4. **Answer only from them.** The model is told to answer only from those excerpts, and to reply with no answer when they don't clearly cover the question. It never guesses. The question is wrapped as data that must not be followed, like every report.
5. **Show it, or fall back.** A usable answer (up to 1,500 characters, plain text) comes back as `200 {"received": true, "answer": "…"}`, and the widget shows it as text, never as HTML. Otherwise the customer gets the usual short reply saying the question was passed to the team.

Answering has its own 12-second budget, after triage's 8, so the reply still arrives before the widget stops waiting at 25 seconds.

## Add help docs

Pass any Markdown or plain text as `helpDocs`. It's searched together with the README, up to 90,000 characters in total:

```ts title="app/api/blaze/route.ts"
import { readFileSync } from 'node:fs';
import { createHandler } from 'blazeresolver/handler';

const handler = createHandler({
  repo: 'acme/shop',
  helpDocs: readFileSync('docs/help.md', 'utf8'),
});

export const maxDuration = 60;
export const POST = handler;
export const OPTIONS = handler;
```

**Write docs that match how customers ask.** Give each task its own heading, and use the words your customers use in headings and first sentences. Without [semantic search](#semantic-search), ranking is by keywords only, so a customer asking to "delete my account" won't find a section that only says "close your account".

## Semantic search

When a provider with an embeddings API has a key configured, sections are also found by meaning, so "remove my profile" finds "Closing your account". There's nothing to set up beyond the key: the same keys as your [AI providers](/docs/setup/ai-providers) are used, and there's no vector store.

| Provider | Found from | Default model |
| :--- | :--- | :--- |
| Any OpenAI-compatible endpoint | `BLAZE_EMBED_BASE_URL` (plus `BLAZE_EMBED_API_KEY`, `BLAZE_EMBED_MODEL`) | set with `BLAZE_EMBED_MODEL` |
| OpenAI | `OPENAI_API_KEY`, or an OpenAI key in `API_KEYS` | `text-embedding-3-small` |
| Voyage AI | `VOYAGE_API_KEY` | `voyage-3.5-lite` |
| Gemini | `GEMINI_API_KEY` / `GOOGLE_API_KEY`, or a Gemini key in `API_KEYS` | `gemini-embedding-001` |
| Mistral | `MISTRAL_API_KEY` | `mistral-embed` |
| Cohere | `COHERE_API_KEY` / `CO_API_KEY` | `embed-v4.0` |
| NVIDIA NIM | `NVIDIA_API_KEY`, or an `nvapi-` key in `API_KEYS` | `nvidia/nemotron-3-embed-1b` |
| Azure OpenAI | the Azure key and endpoint, plus `AZURE_OPENAI_EMBEDDING_DEPLOYMENT` | your deployment |
| Ollama (local) | `OLLAMA_BASE_URL` or `OLLAMA_EMBED_MODEL` | `nomic-embed-text` |

- **One provider, the first configured in that order.** It's never swapped for another mid-way, because vectors from different models can't be compared. `BLAZE_EMBED_PROVIDER` pins one (or `off` for keywords only), and `BLAZE_EMBED_MODEL` changes its model. Anthropic, Groq and most chat-only hosts have no embeddings API; with only those, search stays keyword-only. Run `npx blazeresolver providers` to see which is in use.
- **Each section is embedded once, ever.** Vectors are kept in a vector database inside your product (see below), so a restart or a new instance doesn't embed your docs again. When your docs change, only the sections that changed are embedded again.
- **It never holds up a reply.** Search waits at most 4 seconds for embeddings, then answers from keywords while the docs finish embedding in the background for the next question. A provider that errors is left alone for a minute.
- **Faint matches are dropped.** A section less alike than a cosine similarity of 0.25 doesn't count as a semantic match. Models spread their scores differently; raise `BLAZE_EMBED_MIN_SIMILARITY` if unrelated sections reach the model, or lower it if good ones are missed.

To choose in code, pass `embed` to `createHandler`: an embedder from `resolveEmbedder`, your own `{ id, embed(texts, kind) }`, or `false`.

## What it doesn't do

- **No bug is answered.** Bugs and outages always go to the fix workflow.
- **Nothing is filed for questions**, answered or not. If you want unanswered questions in your support tool, wrap the handler. See [Library API](/docs/reference/library).
- **No links or Markdown are invented.** Answers are plain text, and only contain links that appear in your docs.

## The vector database

Semantic search keeps your docs' vectors in a database in your product, set up on first use with nothing to install or run:

- **By default, a SQLite file in your repo:** `.blazeresolver/vectors.db` at the root of the checkout, through Node's built-in SQLite. It's never committed: `init` adds `.blazeresolver/` to your root `.gitignore` (and the handler adds it too, the first time it creates the database in a checkout that doesn't ignore it yet), with a `.gitignore` inside the folder as a backstop. `npx blazeresolver remove` deletes the database and takes that line back out. Set `BLAZE_VECTOR_DB` to put it elsewhere. On a read-only filesystem (most serverless hosts) it goes to the temp directory, and without a writable disk the vectors are kept in memory.
- **Or your own database**, so every instance shares one copy:

```ts
import Database from 'better-sqlite3';
import postgres from 'postgres';
import { createHandler, sqliteVectorStore, postgresVectorStore } from 'blazeresolver/handler';

// A SQLite database you already have (better-sqlite3 or node:sqlite)
createHandler({ repo: 'acme/shop', vectorStore: sqliteVectorStore(new Database('app.db')) });

// Postgres through any client (a real[] column, no extension needed)
const sql = postgres(process.env.DATABASE_URL!);
createHandler({ repo: 'acme/shop', vectorStore: postgresVectorStore((text, params) => sql.unsafe(text, params)) });
```

The store only keeps vectors, in a `blazeresolver_vectors` table keyed by a hash of the embeddings model and the section. Matching is done exactly, in memory, over your product's own sections: help docs are small enough that an approximate index would gain nothing. `vectorStore: false` keeps vectors in memory only. `createSupportHandler` takes the same `vectorStore` and `readmePath` options.

## Privacy

The matching sections of your README and help docs, and the customer's question, go to your AI provider. With semantic search on, all of your README and help docs, and the question, also go to your embeddings provider. Only include docs you're happy to send there.
